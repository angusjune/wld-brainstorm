# WLD Prototype

Build high-fidelity WeChat Mini Program demos for WLD (微粒贷) from an existing visual source. The demo should feel like a real Mini Program screen, not an HTML mockup or loose code sketch.

**Required source before coding:** the user must provide one of:
- A Figma link to the exact screen or UX flow
- A design generated by `wld-design:brainstorm` in this plugin, including the screen file or flow directory

If neither exists, stop and ask for one. Offer: "I can first generate the design with `wld-design:brainstorm`, then turn the approved result into a Mini Program demo." Do not build from a vague text-only idea.

**Bundled Mini Program template:** copy from `<plugin-root>/plugins/wld-design/skills/prototype/assets/miniprogram-template`. This template ships with the plugin and contains a small WLD app shell, core components, two example pages, styles, and mock product data. Do not depend on any machine-local WeChat project.

**Figma MCP reference:** before reading or exporting a Figma source, read `<plugin-root>/plugins/wld-design/assets/figma-mcp.md` for provider-neutral tool discovery, URL parsing, read flow, and fallbacks.

## Workflow

1. **Confirm the design source**
   - If the user provided Figma, read the frames with Figma MCP when available. If Figma MCP is unavailable, ask for exported screenshots plus frame notes, or offer to use `wld-design:brainstorm` first.
   - If the user provided a brainstorm output, read the generated HTML screens plus `plugins/wld-design/assets/tokens.css`, `plugins/wld-design/assets/components.css`, `plugins/wld-design/assets/mockup-chrome.css`, and the nearest `plugins/wld-design/assets/screens/` templates.
   - If anything is ambiguous, ask one targeted question at a time until the source, flow order, states, interactions, and copy are explicit. Do not guess.

2. **Study the bundled implementation references**
   - Read `plugins/wld-design/assets/DESIGN.md` and the closest files in `plugins/wld-design/assets/screens/` for visual rules.
   - Read `<plugin-root>/plugins/wld-design/skills/prototype/assets/miniprogram-template/app.json`, `app.wxss`, and the closest page/component files before writing Mini Program code.
   - Prefer existing Mini Program components and patterns over custom one-off markup.

3. **Create a separate demo project**
   - If the user gives no output path, create `wld-miniprogram-demo-{slug}` under the current working directory.
   - Start by copying the bundled template directory into the demo project, then edit the copied files.
   - Do not write into this plugin's generated provider folders.
   - Do not modify bundled product knowledge caches.
   - Do not modify the bundled template in place during a user demo task.
   - Do not copy `node_modules`.

4. **Implement the Mini Program**
   - Use real Mini Program files: `.wxml`, `.wxss`, `.js`, `.json`, `app.json`, `app.wxss`, and `project.config.json`.
   - Use `rpx`, WeChat Mini Program components, `wx:if`, `wx:for`, `bindtap`, `Component`, and `Page` APIs. Do not write browser-only HTML/CSS/DOM code.
   - Match the provided visual source exactly: hierarchy, spacing, typography, WLD gold buttons, backgrounds, nav bar, safe areas, bottom actions, sheets, keyboard states, and empty/error/loading states.
   - Preserve Chinese product copy unless the user explicitly changes it.
   - Implement the clickable path the user expects, even if backend data is mocked locally.

5. **Verify before handoff** — run the bundled verifier, do not hand-check the project:

   ```bash
   node "<plugin-root>/plugins/wld-design/skills/prototype/verify-miniprogram.mjs" <demo-project-dir>
   ```

   It runs two layers and exits non-zero on static errors:
   - **Static (always — no deps, no DevTools):** `app.json` parses and lists pages; every page and every `usingComponents` component (recursively) has its `.wxml` / `.js` / `.json`; tabBar pages/icons exist; `.wxml` uses Mini Program tags, not web tags (`<div>` / `<span>` / `<img>` …); no `100vh` in containers wrapped inside `wld-page`; no browser-only globals (`document` / `window` / `localStorage`) in `.js`.
   - **Live (optional, best-effort):** if `miniprogram-automator` is installed **and** the WeChat DevTools CLI is found (default macOS path or `WX_DEVTOOLS_CLI`), it launches the project — a real compile — and screenshots the first page. Otherwise it prints how to enable it and continues; missing tooling is never fatal.

   Fix every reported error and re-run until static verification passes. To enable the live layer, run `npm i -D miniprogram-automator` in the demo project, install WeChat DevTools, and turn on 设置 → 安全设置 → CLI/HTTP 调用 (a preview QR additionally needs `miniprogram-ci` with the project's Upload Key + IP allowlist). Report the verifier's summary and any warnings to the user — do not claim the demo works beyond what the verifier confirmed.

5b. **Match the demo to the design** *(optional — when an approved design reference exists; needs WeChat DevTools)* — close the visual gap instead of eyeballing it:
   - **Capture** each screen from the running demo: `node "<plugin-root>/plugins/wld-design/skills/prototype/capture-miniprogram.mjs" <demo-project-dir>` → writes `.conform/impl/*.png`.
   - **Acquire references** into `.conform/ref/`, one PNG per screen using the **same basename** as its impl screenshot — either a Figma `get_screenshot`, or `node "<plugin-root>/plugins/wld-design/skills/prototype/render-html-reference.mjs" <approved.html> <project>/.conform/ref/<screen>.png` for a brainstorm source.
   - **Compare:** `node "<plugin-root>/plugins/wld-design/skills/prototype/conform-to-design.mjs" <demo-project-dir>` → writes `[ref | impl | diff]` composites + `manifest.json` (mask the status bar with `--mask x,y,w,h`).
   - **Read each composite**, list the concrete mismatches (color / size / weight / spacing / position) with the design as ground truth, fix the demo `.wxss`/`.wxml`, then re-capture and re-run. `driftPct` is a coarse convergence signal only — stop when screens align or after ~3–4 iterations.
   - Full protocol, setup, and limits: `<plugin-root>/plugins/wld-design/skills/prototype/conform-design.md`.

6. **Explain how to preview on a phone**
   - Finish with clear, simple Chinese steps written for a non-technical PM. Use short numbered steps and plain words.
   - Include: open WeChat DevTools, import the project folder, choose a test AppID if needed, click Compile, click Preview, scan the QR code with WeChat on the phone.
   - Mention common blockers in simple language: install WeChat DevTools, log in, keep phone and computer online, use real-device preview for final checking.

## Fidelity Rules

- **Traceability:** every implemented screen must map back to a Figma frame or brainstorm-generated screen.
- **No invention:** if the source does not show a state, behavior, amount, or CTA result, ask before adding it.
- **WLD look:** follow the WLD palette and component proportions from `assets/DESIGN.md`, `assets/screens/`, and the bundled Mini Program template.
- **Mini Program realism:** use native Mini Program structure and interactions, not a web page wrapped in a project.
- **Safe copy:** keep risk, money, interest, coupon, and repayment copy exact. Ask before rewriting regulated or money-related wording.
- **Small-screen fit:** verify long Chinese copy, bottom buttons, keyboard, drawers, and safe-area padding on a real-phone-sized viewport.

## Mini Program Common Mistakes

- **Do not use `100vh` inside `wld-page`; use `100%` instead.**
     `wld-page` already owns viewport height, nav offset, safe-area padding, and scrolling. A child with
     `100vh` becomes taller than the usable content area and can cause clipped bottom CTAs, double
     scrolling, or content hidden under the custom nav.

     ```css
     /* Good */
     .screen {
       height: 100%;
       display: flex;
       flex-direction: column;
     }

     /* Bad */
     .screen {
       height: 100vh;
     }
     ```
